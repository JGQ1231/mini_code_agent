# 架构设计文档
> 基于 mini_code_agent v0.1 版本，说明项目分层结构、模块职责边界、技术选型逻辑与设计原则，作为后续版本迭代的架构基线。

## 1. 我用到的代码
### 项目目录结构
```text
mini_code_agent/
├── src/code_agent/
│   ├── __init__.py
│   ├── __main__.py    # 包启动入口
│   ├── cli.py         # 交互层：命令行入口
│   ├── llm.py         # 业务层：大模型调用封装
│   └── schemas.py     # 数据层：结构体定义
├── .env
├── .env.example
├── .gitignore
└── requirements.txt
```

### 分层调用关系（代码示意）
```python
# cli.py 调用 llm.py（交互层 → 业务层）
from .llm import LLMClient

# llm.py 调用 schemas.py（业务层 → 数据层）
from .schemas import BaseAnswer
```

### 包启动入口
```python
# __main__.py
from .cli import app

if __name__ == "__main__":
    app()
```

## 2. 我的理解
1. **三层分层架构**
    项目采用自底向上的三层结构，职责单一、单向依赖：
    - 数据层（schemas.py）：定义数据模型与校验规则，不依赖任何业务逻辑，是最底层的“数据契约”。
    - 业务层（llm.py）：封装核心业务能力——大模型调用、配置读取、异常处理，只依赖数据层，不关心上层用什么方式交互。
    - 交互层（cli.py）：负责终端用户交互、命令解析、结果美化输出，只调用业务层，不触碰底层请求细节。
    单向依赖的好处是：后续想新增 Web 界面、GUI 界面，只需要新增交互层，业务层和数据层完全不用改动。

2. **配置与代码分离原则**
    密钥、模型地址等配置全部放在 `.env` 文件中，代码只通过 `os.getenv()` 读取，不硬编码任何敏感信息。既保证了密钥安全，也方便在不同环境（本地、部署）切换配置，不用改源码。

3. **包结构设计**
    所有源码放在 `src/code_agent` 包下，通过 `__init__.py` 标记为 Python 包，统一用 `-m` 模块方式启动。好处是模块导入规范、相对导入清晰，后续新增模块（如 rag、agent）可以直接在包内扩展，目录结构不会混乱。

4. **异常封装设计**
    底层的网络异常、格式校验异常，统一在 llm.py 中包装为 `RuntimeError` 抛出，上层 cli 只需要捕获通用运行时错误，不用感知底层具体异常类型，降低了层与层之间的耦合。

## 3. 踩坑
### 坑1：包结构不规范导致相对导入失效
#### 报错信息
```text
ImportError: attempted relative import with no known parent package
```
#### 现象
初期直接把 py 文件堆在根目录，相对导入一直报错。
#### 原因
没有遵循 Python 包规范，缺少包标记文件、启动方式不是模块模式，Python 无法识别包层级。
#### 解决
统一使用 `src/code_agent` 包结构，补充 `__init__.py` 和 `__main__.py`，全部通过 `python -m` 模块方式启动，相对导入完全正常。

### 坑2：交互层和业务层混写导致扩展困难
#### 现象
初期把 LLM 调用逻辑直接写在 cli.py 里，代码很短但想加新功能时要改很多地方。
#### 原因
没有分层，交互逻辑和业务逻辑耦合在一起，后续新增功能会导致单文件越来越臃肿。
#### 解决
拆分为 schemas / llm / cli 三层，每层职责单一，后续新增能力只需要在对应层级扩展。

### 坑3：单命令模式属于交互层设计问题
#### 现象
只有一个 ask 命令时，Typer 自动进入单命令模式，和预期的子命令用法不符。
#### 原因
架构分层没问题，但 CLI 层的命令数量触发了框架的隐式行为，属于交互层的框架特性坑，不影响底层架构。
#### 解决
v0.2 新增第二条子命令即可退出单命令模式，底层业务代码无需修改，体现了分层解耦的优势。
