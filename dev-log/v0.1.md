## 2. 我的理解
1. **本版本目标**
    搭建最小可用的命令行本地AI编程助手，跑通「用户输入问题 → 调用大模型接口 → 结构化校验返回 → 终端彩色输出」的完整闭环，搭好可扩展的工程骨架。

2. **分层设计思路**
    采用三层解耦结构：schemas 负责数据定义与校验、llm 负责大模型请求与异常封装、cli 负责终端交互与输出。后续新增功能只需要在对应层级扩展，不用改动整体架构。

3. **技术选型理由**
    - Typer：基于类型注解自动生成命令行，比手写 argparse 代码量更少、帮助文档更规范，适合快速搭建CLI工具。
    - Pydantic：大模型输出不可控，用 Pydantic 强制校验JSON格式，能从底层拦截格式异常，避免上层业务崩溃。
    - python-dotenv：实现配置与代码分离，API密钥不硬编码，避免误提交到代码仓库造成泄露。

4. **本版本遗留问题**
    - 无多轮对话能力，每次提问均为独立会话，上下文不互通。
    - Typer 处于单命令模式，`ask` 无法作为子命令使用，调用方式不符合直觉。
    - 无日志记录与错误分级，异常统一包装为 RuntimeError，排查问题粒度不足。

5. **下一步（v0.2 方向）**
    新增第二条子命令退出 Typer 单命令模式，补充基础日志输出，优化错误提示的分级与可读性。

## 3. 踩坑
### 坑1：Typer单命令模式导致ask子命令失效
#### 报错信息
```text
Usage: python -m src.code_agent [OPTIONS] {question}
Try 'python -m src.code_agent --help' for help.

Error: Got unexpected extra argument(s) (解释Pydantic的作用)
```
#### 现象
执行 `python -m src.code_agent ask "解释Pydantic的作用"` 时报错，提示存在多余的位置参数。
#### 原因
应用内仅注册了 `ask` 一个命令，触发 Typer 单命令模式，命令名被隐去，`ask` 被识别为参数值而非子命令。
#### 解决
- 临时方案：去掉命令名，直接 `python -m src.code_agent "问题"` 调用。
- 长期方案：新增第二条子命令，自动退出单命令模式，恢复子命令用法。

### 坑2：相对导入必须用 -m 模块方式启动
#### 报错信息
```text
ImportError: attempted relative import with no known parent package
```
#### 现象
直接运行包内单个 py 文件时，报相对导入错误。
#### 原因
直接运行单个文件时，Python 将其视为独立脚本，无法识别所属的包层级，`.` 开头的相对导入没有父包上下文，因此失效。
#### 解决
统一使用 `python -m src.code_agent` 模块方式启动，确保包结构被正确识别；禁止直接单独运行包内的业务文件。

### 坑3：ValidationError 拼写错误
#### 报错信息
```text
ImportError: cannot import name 'ValiadationError' from 'pydantic'
Did you mean: 'ValidationError'?
```
#### 现象
导入 Pydantic 异常类时报错，提示找不到对应名称。
#### 原因
手动输入时字母顺序错误，将 `ValidationError` 误写为 `ValiadationError`。
#### 解决
修正拼写为 `ValidationError`；导入类名优先对照官方文档，避免凭印象手写。

### 坑4：.env 配置不生效
#### 报错信息
```text
RuntimeError: 调用大模型失败: You didn't provide an API key.
```
#### 现象
程序启动后调用大模型时报认证错误，提示缺少 API 密钥。
#### 原因
常见原因包括：仅修改了 `.env.example` 未生成 `.env`、变量名大小写不匹配、文件不在项目根目录、等号前后有多余空格。
#### 解决
复制 `.env.example` 生成 `.env` 并填入真实密钥；确认文件位于项目根目录；核对变量名与代码中 `os.getenv()` 的参数完全一致。
